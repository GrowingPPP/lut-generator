## 1. 目标与范围

用户在「生成」页上传一张照片,点一下按钮,系统自动分析照片并产出一版调好的 LUT;展示原图/修图后对比与文字说明,用户可继续拖滑杆微调,然后保存或下载。

**范围(已确认)**

| 项 | 决定 |
|---|---|
| 范围 | 全局影调色彩自动优化 **+ 风格化**(用户可选风格) |
| 触发 | 一键自动;完成后可继续手调 |
| 闭环 | **双通道**:数字硬校验 + 图像主观复检 |
| 风格来源 | **用户自然语言描述**(非固定预设) |
| 与已有手调的关系 | **增量**:基于当前参数调整,不从默认值重来 |
| 图像通道 | **默认开启**,可关 |

**明确不做**:位置相关(暗角、渐变/径向滤镜、蒙版、局部画笔、修复类)与邻域相关(清晰度、纹理、去雾、锐化、降噪)的运算。

这不是「暂时不做」,而是**类型不匹配**:3D LUT 是逐点映射 `f(r,g,b)`,签名里没有位置、也没有邻域,
所以暗角与锐化在数学上就写不进去。完整的边界说明见[技术设计 §4](./technical.md#4-调色参数全集30-个与-lut-能力边界)。

边界清晰带来一个实际好处:30 个参数全部能烘进**单个** 33³ `.cube`,机内烧录与后期软件两条路都成立。
一旦引入位置相关运算,就必须导出「LUT + 蒙版/工程文件」,机内烧录直接作废 —— 那才是真正的产品形态变化。

**输出形态**:始终是**一个** `.cube`(33³)。优化与风格化在**参数空间合并**成一次变换。

### 1.1 为什么必须合并成单个 LUT

一个自然的冲动是「先自动修正基本问题,再套风格 LUT」。**这条路是错的**:

1. LUT 会被应用两次。相机机内烧录(Real-Time LUT)与后期软件(DaVinci/PR)两条路径都会重复叠加,结果与预览不一致。
2. 单个 `.cube` 无法表达两段变换的串联。

因此:两阶段只在**参数与判定**上分两步,最终仍然只调用一次 `generate_lut()` 产出单个 LUT。这与现有架构天然契合 —— 数学引擎不需要任何改动。

## 2. 已验证的技术前提

| 结论 | 来源 |
|---|---|
| `deepseek-flash` 支持图像输入(JPEG/PNG/GIF/WebP) | [官方图像理解文档](https://api-docs.deepseek.com/zh-cn/guides/vision) |
| 图片 token **每张上限 1024**,与原图大小无关(自动缩放到约 1300×1300) | 同上 |
| `detail: "low"` 可缩到 512×512,更快更省 | 同上 |
| 图片只能出现在 `user` 消息;放 `system`/`assistant` 会 400 | 同上 |
| **模型能可靠地把统计数字读成诊断** | **实测**:见 §2.1 |
| **模型能分辨渲染前后并给出有价值的主观复检** | **实测**:见 §2.2 |
| `generate_lut(33³)` 仅 **6.5 ms**,`lut_to_cube` 43 ms | 本机实测 |

### 2.1 实测:通道 1(统计 → 参数)

输入一张合成「欠曝 + 偏暖 + 低对比」图,仅给统计数字:

```
统计:  lum_p5=0.286  lum_p50=0.392  lum_p95=0.495  R-B差=0.167  sat=0.213
模型:  「画面低反差发灰(亮度区间仅 0.29-0.50)、整体偏暖黄(R-B 差 0.167)、曝光略欠」
提议:  exposure +0.25, contrast +0.45, temp -450, lift 负值压黑
```

模型确实从分位数读出「发灰」、从通道差读出「偏暖」,幅度合理,耗时 5.3s。

### 2.2 实测:通道 2(双图主观复检)

把原图与渲染结果一起发给模型(`detail:low`),耗时 3.2s / 876 token:

> 「套用 LUT 后饱和度和对比度明显提高……但问题在于 LUT 把噪点和色阶断层放大成明显的色块、色带,画面反而更脏。」

模型识破了测试图是合成噪点,并指出了 LUT 会放大噪点 —— 这是**真实的图像推理**,不是套话。这条能力对「修过头」的拦截很有价值。

## 3. 架构

```
                     ┌─ 一键自动修图 ─────────────────────────────┐
用户上传照片 ─────────┤  (可选)风格描述:自然语言                  │
                     └──────────────────────────────────────────┘
                                    ↓
①  测量层(numpy/PIL,零 token,可复现)
    photo/stats.py → PhotoStats
                                    ↓
②  判定层(确定性规则)
    photo/quality.py → [Issue...]        「修什么」由规则定,不靠模型泛谈
                                    ↓
③  提议层(LLM,阶段 A:优化)
    propose_correction(当前参数, stats, issues)         ← 增量,基于当前参数
                                    ↓
④  应用 + 重测(43 ms)
    lut_engine + stats → 新 stats
                                    ↓
⑤  硬校验(确定性,不可绕过)
    高光/阴影裁剪不得增加、肤色均值漂移受限 …
    不合格 → 回退该提议,回到 ③(最多 2 轮)
                                    ↓
⑥  阶段 B:风格化(仅当用户给了风格描述)
    ⑥a 自然语言 → 参数增量(复用现有 describe 抽取路径)
    ⑥b 叠加到 ⑤ 的结果上,再过一次 ⑤ 的硬校验
                                    ↓
⑦  主观复检(LLM,视觉,默认开)
    原图 vs 渲染图 → 复检意见;若判定「修过头」可回退
                                    ↓
⑧  产出:单个 LutParams → 单个 .cube
    + 修改说明(诊断 + 各步调整 + 风格理解 + 复检结论)
```

**核心原则:用眼睛看的是代码,用脑子想的是模型。**

模型不直接猜参数后盲发,而是基于 ① 的客观测量给出靶向修正;⑤ 用确定性规则否决错误提议。没有 ①,模型只能给放之四海皆准的建议;没有 ⑤,模型的错误提议会直接污染用户照片。

### 3.1 两条闭环通道的分工

| | 通道 1:数字 | 通道 2:图像 |
|---|---|---|
| 输入 | `PhotoStats` 数字 | 原图 + 渲染图 |
| 判定 | **硬**:可测量、可回归、不可绕过 | **软**:主观观感、修过头、不自然 |
| 用途 | 通过/拒绝 + 驱动下一轮 | 参考意见 + 触发回退 |
| 成本 | 低(无图 token) | 每轮约 2×1024 图 token |
| 为何不合并 | 数字无法判断「是否自然」;图像无法给出可靠数值 | |

⚠️ **不要让图像通道直接产参数。** VLM 对精确色彩数值的判断不可靠(实测中它明确说了「不要给参数」的约束下表现最好)。图像通道只产出**文字复检意见**,意见再作为通道 1 下一轮的输入。

### 3.2 增量语义(已决策:基于当前参数)

自动修图**永远基于当前参数增量化**,不从默认值重来。三个后果:

1. **保留用户意图。** 用户已经手动调过色温,自动修图应该在此基础上继续,而不是把它抹掉。
2. **可以反复点。** 点两次 = 修正两轮,是**特性而非 bug**。第一次修曝光、第二次修色偏,叠加生效。但仍需轮数上限(建议 3),防止无限叠加导致越修越糟 —— 累计效果一样要过 §4.3 的硬校验。
3. **风格阶段也基于「优化后」的参数**,而不是原始参数(否则优化白做)。

实现上不需要新机制:现有 `/api/session/chat` 已经是「参数增量叠加」语义(前端传当前参数,LLM 只返回被提及字段),直接对齐即可。

### 3.3 自然语言风格描述(已决策)

风格不走固定预设,而是用户自由描述(如「日系清透一点」「电影青橙,暗部带蓝」)。这样更灵活,但需要新增一个**抽取环节**。

**关键设计:复用现有抽取路径,不要新写一套。**

`agent/schemas.py` 的 `ExtractResult` 能表达全部 30 个参数(含 `base_photo_style`、`tone_map`、风格强度、局部色彩及 `lift/gamma/gain`),而 `agent/llm.py` 的 tool calling 使用同一参数模型。所以 ⑥a 是**同一个工具的复用**:

```
阶段 A(优化)  propose_correction   → 工具入参:诊断相关的修正量
阶段 B(风格)  extract_style        → 工具入参:复用 ExtractResult 的字段
```

两者共用 `build_tool_schema()` 的 schema 生成逻辑,只是工具描述与系统提示不同。**不要为风格另立一套参数字典** —— 那会导致「风格参数」和「调色参数」两套定义漂移,而项目已经吃过双实现漂移的苦(JS/Python 引擎需要 parity 校验)。

风格的 `intent` 语义需要调整:风格描述必然走 `describe`(它不会说「确认」),因此阶段 B 可以忽略 `intent`,只取参数字段。

**风格阶段也要过硬校验。** 「日系清透」常被模型实现为「大幅提亮 + 加饱和」,容易冲掉高光;风格不能成为绕过 §4.3 的后门。

**风格描述的抽取会受 `intent` 规则干扰吗?** 不会 —— 但要注意 `ExtractResult.intent` 是必填字段,复用时应传一个中性的系统提示(明确「这是一次风格描述,请提取风格参数」),或在 schema 里为风格场景单独构造一个 `intent` 已固定的工具定义。

## 4. 模块划分与职责

| 模块 | 职责 | 是否依赖 LLM |
|---|---|---|
| `photo/stats.py` | 图像 → 客观测量(`PhotoStats`) | 否 |
| `photo/quality.py` | 测量 → 问题清单(`Issue`)+ 硬校验上限 | 否 |
| `photo/render.py` | LUT + 图像 → 渲染结果(向量化三线性) | 否 |
| `photo/fixtures.py` | 合成测试图(带已知缺陷) | 否 |
| `agent/auto.py` | 编排:优化 → 硬校验 → 风格 → 复检 | 是 |
| `api/main.py` | `POST /api/auto/grade` | 否 |
| 前端 `AutoRetouchBar` / `AutoRetouchReport` | 一键触发、进度、说明、撤销 | 否 |

**依赖方向不可逆**:`api → agent.auto → photo.* → numpy/PIL`。
`photo/*` **不得** import fastapi / openai / storage —— 它是纯函数层,必须能脱离框架单测。

**接口签名、数据结构、阈值常量、API 契约、样式规格全部见[技术设计](./technical.md)**,本文不重复。

### 4.1 为什么测量与判定要分成两层

直接把数字丢给模型也能 work(§2.1 实测证明了),但拆出 `quality.py` 带来三个好处:

1. **阈值可测、可调、可回归** —— 纯函数,改一个数字就知道影响面
2. **省 token** —— 只传命中的问题,而不是几十个原始数字
3. **可解释** —— `Issue.evidence` 直接变成给用户看的说明文字,一份文案同时服务模型与人

### 4.2 硬校验规则(为何是这几条)

规则表与阈值见[技术设计 §7.2](./technical.md#72-硬校验)。这里只说明选取理由:

- **只校验「可测量且单调」的量**(裁剪、肤色漂移、饱和度上限)。主观项(「够不够通透」)不放进硬校验 —— 那需要审美判断,交给⑦。
- **R1/R2 对比上一轮,R4 对比最初基线**。这个区分是刻意的:前者防单轮突变,后者防多轮累加绕过。混用会让 R4 形同虚设(测试方案里有专门的绕过用例)。
- **保守解不依赖 LLM**。曝光与白平衡的修正是可计算的(相机自动测光就是同一原理),所以兜底路径可以完全确定。

## 6. 成本与延迟预算

| 阶段 | 实测/预算 | 说明 |
|---|---|---|
| ① 测量 | < 30 ms ×6 次 | 512px 降采样 |
| ④ 渲染 | 18 ms(240×320) | numpy 三线性,无新依赖 |
| ③ LLM 提议 | **5.3 s**(实测) | 通道 1,无图 token |
| ⑥a 风格抽取 | ≈ 2 s(预算) | 复用现有抽取路径 |
| ⑦ 视觉复检 | **3.2 s / 876 token**(实测) | 双图 `detail:low` |
| **合计** | **约 10~15 s** | 目标 < 15 s |

关键结论:**真正的成本全在 LLM 往返,本地计算可忽略(合计 < 0.3 s)**。所以优化方向是减少 LLM 轮数(§4 的收敛判定),而不是优化 numpy。

## 7. 已知风险与取舍

| 风险 | 应对 |
|---|---|
| **模型诊断不稳定**(同一张图两次建议不同) | 硬校验兜底;`temperature` 在思考模式下无效,故靠规则而非调温;可考虑对 `stats` 做分桶降低敏感度 |
| 图像通道成本随轮数线性增长 | 默认 `detail:low`(512×512);轮数上限 2;可配置关闭通道 2 |
| VLM 对「自然度」的判断可能与真人审美不一致 | 通道 2 只作为**参考意见**,不单独决定回退;回退需同时有数字证据或明确「修过头」判词 |
| 自动修图可能放大噪点(实测中被模型指出) | 在 `stats` 里加噪声估计,超标时限制 `contrast`/`saturation` 上限 |
| 用户照片隐私 | 图片不落库;明确告知会发送给模型;提供关闭图像的选项(退化为纯数字通道,已决策默认开、可关) |
| 一键修图结果不符合预期 | 必须可撤销;展示完整推理过程,让用户理解为什么这么调 |
| **反复点导致过度叠加** | 增量语义下这是真实风险(「越修越艳」)。三重防线:每轮都过 §4.3 硬校验、累计轮数上限 3、一键撤销 |
| **自然语言风格被理解偏** | 单独返回 `style_params` 让用户核对;风格描述走与现有对话相同的抽取路径,用户已熟悉该交互 |
| **风格成为绕过校验的后门** | 风格阶段结束后**必须再过一次硬校验**,与阶段 A 同一套规则 |

## 8. 实施顺序(建议)

分 4 个可独立验证的阶段,每阶段结束都能跑通:

1. **测量 + 判定**(`stats.py` + `quality.py` + 测试)—— 纯后端,无 LLM,最容易验证
2. **通道 1 闭环 + 增量语义**(`auto.py` 优化部分 + 硬校验 + API)—— 能出一版结果了
3. **前端一键交互**(按钮 + 风格输入框 + 对比 + 说明 + 撤销)
4. **风格化抽取 + 通道 2 主观复检** —— 增量,各自可独立开关

阶段 1、2 完成时功能已可用;3 之后可交付;4 是增强。这样任何一步中断都不会留下半成品。

每阶段的验收标准:

| 阶段 | 验收 |
|---|---|
| 1 | `photo/` 的 L1 测试全绿(测量正确、阈值有边界测试),**不需要 API key** |
| 2 | `POST /api/auto/grade` 可用;硬校验 7 条规则各有拒绝用例;降级路径有测试 |
| 3 | Playwright 可跑通「上传 → 修图 → 看对比 → 撤销」;`make check` 全绿 |
| 4 | 风格不可绕过硬校验;关闭视觉后确认不发图 |

## 9. 已决策事项(原「待确认」)

| # | 问题 | 决定 | 影响 |
|---|---|---|---|
| 1 | 风格从哪来 | **用户自然语言描述** | 新增 ⑥a 抽取环节;复用现有 `ExtractResult` 与 tool calling,不另立参数字典(§3.3) |
| 2 | 是否覆盖用户手调 | **增量,基于当前参数** | `base_params` 必填、无默认值兜底;反复点自动修图成为特性,需轮数上限与撤销(§3.2) |
| 3 | 图像通道默认开关 | **默认开、可关** | `use_vision` 默认 true;关闭后退化为纯数字通道,精度下降但零图 token |

三项决定共同收敛到一个好处:**没有一项需要改动 LUT 数学**,全部落在「参数从哪来」这一侧。
