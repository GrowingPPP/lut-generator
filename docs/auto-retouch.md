## 一句话概括

**用眼睛看的是代码,用脑子想的是模型。**

图片的客观测量交给 numpy(确定性、零 token、可回归),模型只负责「问题 → 参数」的映射;每一轮提议都要过一道与模型无关的确定性硬校验,不合格就回退重提,再不达标就用可计算的保守解兜底并如实告知。

## 三个已决策事项

| 项 | 决定 |
|---|---|
| 风格来源 | 用户**自然语言描述**,复用现有 tool calling 抽取路径,不另立参数字典 |
| 与手调的关系 | **增量**:基于当前参数叠加,不从默认值重来 |
| 视觉复核 | **默认开启**,可关闭(关闭后只发数字,不发图) |

## 已验证的技术前提

标注「实测」的都在本机真接口上跑过:

| 结论 | 来源 |
|---|---|
| `deepseek-flash` 支持图像输入;每张图 token 上限 1024,与原图大小无关 | 官方文档 |
| 模型能从统计数字读出「发灰」「偏暖」并给出合理幅度 | 实测 |
| 模型能分辨渲染前后,并识破合成噪点、警告 LUT 会放大噪点 | 实测 |
| `generate_lut(33³)` 6.5 ms;手写 numpy 三线性采样 18 ms,**无需新依赖** | 实测 |
| 全链路约 10~15 s,成本几乎全在 LLM 往返(本地计算 < 0.3 s) | 实测 + 预算 |

## 边界

**做**:全局影调色彩自动优化 + 风格化,输出**单个** `.cube`。

**不做**:局部调整、祛痘磨皮、透视校正、去杂物 —— 超出一张 3D LUT 的表达能力。

⚠️ 一个必须避开的坑:不要做「先自动修正、再套风格 LUT」的两段式。那会导致 LUT 被应用两次(机内烧录与后期软件都会重复),且单个 `.cube` 无法表达两段变换的串联。**只在参数空间分两步,最终只调用一次 `generate_lut()`。**

## 对现有代码的影响

**不碰 LUT 数学。** 全部改动落在「参数从哪来」这一侧 —— `lut_engine` 零改动,现有 105 个测试与两道 parity 校验原样继续生效。
