# 遗留问题清单与解决方案

> 来源:AI 自动修图功能交付后的自查。每条都经过**实际查证**,不是推测。
> 顺序按处理优先级,不按发现顺序。
>
> **状态:此清单记录上一轮的 12 个问题与当时的处理结果。** 2026-10-09 全面审核发现的后续问题见 [修复计划](./audit-remediation-plan.md)。文中的测试数量和局限说明属于历史记录。

## 问题汇总

| # | 问题 | 类型 | 影响 | 查证方式 |
|---|---|---|---|---|
| 1 | 每次自动修图新建一个会话 | 功能缺陷 | 会话列表被「自动修图」刷屏 | 实测 5 次调用 → 5 个同名会话 |
| 2 | 自动修图端点无限流 | 成本风险 | 每调一次打一次 LLM(≈11.6s / 5000+ token),可无限刷 | 限流只挂在 auth 端点 |
| 3 | 刷新后修图报告丢失 | 功能缺陷 | 诊断/步骤/被拒/复检全丢,看不到「为什么这么调」 | 后端存了参数,前端只恢复 params |
| 4 | 进度条是假的 | 误导 | 四步骨架瞬间画好,一直停在第 2 步到请求结束 | `i===0?'done':i===1?'running'` |
| 5 | 视觉复核失败静默伪装成「你关的」 | 误导 | 用户以为是自己关的,实际是失败或被跳过 | 三条路径都返回 None |
| 6 | `App.jsx` 952 行 | 技术债 | 单组件管六件事,难改难测 | `wc -l` |
| 7 | 编排层错误被压成通用 502 | 可运维性 | 前端只看到「分析服务暂时不可用」,无法区分超时/限流/上游 5xx | `except Exception` 统一处理 |
| 8 | `emptyLike` 未测 | 技术债 | 报告里风格参数的展示逻辑没测试覆盖 | 内联在组件里 |
| 9 | 视觉复核状态未区分原因 | 可观测性 | 前端无法区分「用户关闭」与「复核失败」 | 与 5 同源 |
| 10 | 上传大小检查位置不当 | 健壮性 | 32MB 存在内存里才检查;超大图报 400 而非 413 | 读完整字节后判断 |
| 11 | 思考预算耗尽无专门处理 | 可运维性 | 会走通用 502,用户看不到「调大 MAX_TOKENS」的可操作提示 | `BudgetExhaustedError` 被上游 catch |
| 12 | 参数格式化有两套实现 | 一致性 | 应用与原型各写一份,可能漂移 | 原型不该被应用 import,应明确边界 |

## 逐个设计

### 问题 1 + 3:合并解决 —— 自动修图复用单一会话,报告可恢复

**为什么合并**:两者是同一个设计的缺口。当前「每次新建会话 + 报告只在前端」,
既刷屏又无法恢复。改为:

```
自动修图 → 复用该用户的「唯一自动修图会话」(不存在则建)
         → 每次结果追加为一条消息,结构化结果存进 payload
GET /api/auto/report → 返回最近一次结构化结果 → 前端重建报告
```

**关键设计决策:用显式标记而不是按标题字符串查。**
按 `title = '自动修图'` 查会话很脆(用户改标题就失效,且标题是展示用文案)。
改为给 `sessions` 加 `is_auto TINYINT` 列,查询走标记。迁移沿用既有幂等风格。

**消息结构化存储**:`messages` 加 `payload_json MEDIUMTEXT`,存完整 `AutoGradeOut`。
不复用 `content` —— 它是给人看的可读说明,混入 JSON 会污染会话展示。
`content` 仍写可读摘要,两者并存。

**收益**:会话列表干净(固定 1 条);刷新后可恢复报告;历史可回溯(后续可做「载入历史报告」)。

### 问题 2:自动修图独立限流(按用户)

复用现有 `ratelimit` 的锁与容量上限模式,但**按 user_id 而不是 IP** 计数
(登录用户换 IP 不应该是绕过手段),窗口更长、阈值更低:

```
AUTO_MAX_PER_WINDOW = 20      # 每用户每窗口
AUTO_WINDOW_SECONDS = 3600    # 1 小时
```

超限返回 **429** 并带 `Retry-After`。不做全局配额(单机足够,共享存储的局限已有文档)。

### 问题 4:改成诚实的不确定进度

服务端是同步的,没有中间进度可报 —— 与其假装有进度,不如承认:

- 显示**不确定态**(旋转指示 + 「正在分析照片…」)
- 四步清单仍展示**将要发生什么**(它是有信息量的),但不逐项标「已完成」
- 唯一能确定的切换:收到结果后一次性全部标记完成

这比假进度更诚实,也不会让用户误以为卡在第 2 步。

### 问题 5 + 9:把「跳过原因」传给用户

`vision_review` 返回 `(review, usage, skip_reason)`,原因是三选一:

| 原因 | 前端展示 |
|---|---|
| `disabled` | 「已关闭视觉复核」(用户自己的选择) |
| `failed` | 「视觉复核未能完成(模型或网络问题),本次仅依据客观数据」 |
| `no_client` | 「未配置模型,跳过视觉复核」 |

`AutoGradeResult` 增 `review_skip_reason` 字段。前端按原因渲染不同措辞 ——
关键是不能把「失败」说成「你关的」。

### 问题 6:拆分 App.jsx

按**职责**拆,不按行数拆:

| 抽出 | 内容 | 预计减行 |
|---|---|---|
| `hooks/useSessions.js` | 会话列表的加载/新建/重命名/删除/打开 | ~90 |
| `components/LibraryView.jsx` | 「我的 LUT」页(含 `makeThumb`) | ~95 |
| `components/AuthView.jsx` | 登录注册 | ~45 |
| `components/usePreview.js` | 预览渲染(已独立的逻辑搬家) | ~90 |

目标:`App.jsx` 降到 ~500 行以下,`GenerateView` 只保留「生成页的编排」。

### 问题 7:区分上游错误原因

`except Exception` 太粗。改为按类型映射,并**保留原因**:

| 异常 | 响应 |
|---|---|
| `APITimeoutError` / `APIConnectionError` | 504「分析服务响应超时,请重试」 |
| `APIStatusError` | 502「分析服务返回错误(状态码 N)」 |
| `BudgetExhaustedError` | 502 + 可操作提示「模型思考预算不足,请调大 CHROMA_LLM_MAX_TOKENS」 |
| 其他 | 502 通用 |

同时把完整异常写进服务端日志(前端只拿简短原因)—— 便于排查又不泄露内部细节。

### 问题 8 + 12:下沉展示逻辑

- `emptyLike` 从组件移到 `lib/autoGrade.js` 作为 `styleDiff()` 并加测试
- 参数格式化统一到 `lib/autoGrade.js` 的 `formatDelta()`;原型保留自己那份,
  在原型文件顶部注释里明确「原型不复用应用代码,两处格式化约定必须一致」,
  并加一条测试比对两侧的单位规则

### 问题 10:上传检查分两段

- **字节数**:在读取前用 `Content-Length` 预判(拿不到就退化为读后判断),超限 413
- **像素数**:交给 `photo.stats`(它已有 `MAX_PIXELS` 与 `ImageTooLargeError`),
  API 层把 `ImageTooLargeError` 单独映射成 **413** 而不是 400

前端加同样的预检,给友好文案而不是等服务端拒绝。

### 问题 11:见问题 7 的异常映射表

`BudgetExhaustedError` 单独成一类,给可操作提示。编排层仍容忍它(走保守解),
但 API 层要把它记进日志,便于发现「预算经常不够」的系统性问题。

## 任务拆分

| 阶段 | 任务 | 交付物 | 验收 |
|---|---|---|---|
| A | 1+3 数据层:迁移 + 复用会话 + payload 存储 + 报告查询端点 | `storage/db.py`、`api/main.py` | 迁移幂等;5 次调用只有 1 个会话;报告可恢复 |
| B | 2 限流:按用户计数 + 429 | `api/ratelimit.py`、`api/main.py` | 超限返回 429;不同用户互不影响 |
| C | 7+11 错误映射 | `api/main.py` | 四类异常各有对应状态码与可操作文案 |
| D | 10 上传检查分段 | `api/main.py`、前端预检 | 超大图 413;前端提前拦截 |
| E | 5+9 视觉复核原因 | `photo/types.py`、`agent/auto.py`、前端 | 三种原因三种措辞;失败不再伪装成「已关闭」 |
| F | 4 诚实进度 | `AutoRetouchBar.jsx` | 不再显示虚假的「已完成」步骤 |
| G | 8+12 展示逻辑下沉 | `lib/autoGrade.js`、组件、原型注释 | `styleDiff` 有测试;单位规则一致 |
| H | 6 拆分 App.jsx | 4 个新文件 | App.jsx < 500 行;E2E 仍通过 |
| Z | 全量回归 | — | `make check` 全绿 + 浏览器 E2E |

**顺序理由**:A→D 是后端数据与边界(先做,后续依赖它们);E→G 是展示层;
H 是纯重构放最后(风险最高,但此时其它改动已稳定,回归信号最干净)。

**每个阶段完成后立即跑 `make check`**,不攒到最后 —— 这样出问题能定位到阶段。

## 处理结果

12 个问题全部解决。回归:**409 后端测试 + 22 前端测试 + 2 个浏览器 E2E 场景**全绿。

| # | 问题 | 解决方式 | 验证 |
|---|---|---|---|
| 1 | 会话刷屏 | 复用单一自动修图会话(按 `is_auto` 标记,不按标题) | 5 次调用 → 1 个会话 |
| 2 | 无限流 | 按 user_id 计数,20 次/小时,超限 429 + Retry-After | 第 4 次起 429 |
| 3 | 报告丢失 | `messages.payload_json` 存完整结果 + `GET /api/auto/report`(带 session_id) | 浏览器实测:刷新→开会话→报告恢复 |
| 4 | 假进度 | 改为不确定态(旋转 + 「正在分析照片…」),四步清单只说明将要发生什么 | E2E 断言进度头存在 |
| 5 | 静默伪装 | `review_skip_reason` 三态,前端按原因给不同措辞 | 三态各有测试 |
| 6 | App.jsx 过大 | 抽出 `usePreview` / `LibraryView` / `AuthView` / `lib/preview.js` | 952 → 658 行(GenerateView 占 468,是功能所在) |
| 7 | 错误压成 502 | 四类异常分别映射 504 / 502+状态码 / 502+可操作提示 / 通用 502,并记日志 | 5 个测试各覆盖一类 |
| 8 | `emptyLike` 未测 | 下沉为 `styleDiff()` 并加 3 个测试 | 前端 22 测试 |
| 9 | 状态未区分原因 | 同 #5 | — |
| 10 | 上传检查 | Content-Length 预判;像素超限单独映射 413 | 2 个测试 |
| 11 | 预算耗尽无提示 | 单独捕获,提示调大 `CHROMA_LLM_MAX_TOKENS` | 1 个测试 |
| 12 | 两套格式化 | 统一到 `autoGrade.js`;原型保留自己那份并在注释里说明边界 | 单位规则测试 |

### 处理过程中新发现的 bug

修 #5 时发现后端把原因判定顺序写错了:

```python
if not use_vision:          # ← client 为 None 时 use_vision 已被算成 False,
    reason = "disabled"     #   于是「没配置模型」被标成「用户关闭」
```

`CHROMA_FAKE_GRADE` 或未配置 key 的部署下,用户会看到「已关闭视觉复核」——
以为是自己关的。修正为**先判 `no_client`,再判 `disabled`**,并补了 4 个测试
锁定三态语义。

这个 bug 单元测试没覆盖到,是**浏览器 E2E 的精确文案断言**抓出来的 ——
说明「断言具体文案」比「断言元素存在」更能发现问题。

### 刻意没做的

- **`GenerateView` 仍是 468 行**:它承载生成页的全部编排(会话、聊天、预览、
  参数、保存下载、自动修图)。继续拆需要引入状态管理方案或大量 props 透传,
  在 409 个测试的保护下也不属于「遗留问题」级别。若要拆,建议先补组件测试。
- **限流仍是单进程内存态**:多 worker 下阈值被放大 N 倍。真修需要共享存储
  (Redis),与当前「无外部依赖」的部署取向冲突,已写进 README 的局限说明。
